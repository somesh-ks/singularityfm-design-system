## DS-7: a component that needs a script renders whole on the server and hydrates as the page loads, with client:load

- Status: active; amends [DS-3](DS-3.md) (client:load, not client:visible or client:idle) and [DS-5](DS-5.md) (the shim of a component that needs hydration carries the directive); its scope narrowed by [DS-8](DS-8.md), which draws Field, Switch and Slider as native elements that need no hydration
- Date: 2026-11-09
- Decision: the rule for a component whose behaviour needs a script the browser does not have: Avatar (the photo's fallback to its shape when it fails to load), the segmented nav (Base UI Tabs), and Code's copy if its family draws the copy in React. A component that works as a native element before any script (DS-8: Field, Switch, Slider, Button, Dialog, Select and the rest) takes no directive and ships no script.
  - One `.tsx` per component, on its Base UI primitive, renders its whole look on the server: every state it is drawn in is in the HTML, so nothing moves when it hydrates and a person can read it before.
  - The page opts in, at the call, with Astro's own directive: `<Avatar client:load ... />`. The library cannot set a directive from a `.tsx` (it is an attribute of the call in an Astro page), and a React island needs none: the component hydrates with the island. In an Astro page a component starts from its `default*` prop and keeps its own state, since a page cannot hold React state; in an island it is controlled.
  - The directive is `client:load` (the owner's call, 2026-11-09). Every island starts loading as the page does, so the window in which a press is lost is as short as the page's own load: no wait for the control to scroll into view, or for an idle main thread, which on a phone still running the page's scripts comes after the first tap more often. The cost is script for components off screen, on the pages that draw them.
  - The deprecated `.astro` shim of a component that needs hydration carries `client:load` itself, so an old call keeps a component that answers. `designSystem.test.ts` allows no directive in a shim until such a family adds one, and that family widens it.
- Measured in the pilot (Field, Switch and Slider on Base UI, Chromium, scripts held back), which led to DS-8: the Field lost nothing; a Base UI Switch drew its state but lost a press (a tap, a click, a click on its label, Space); a Base UI Slider drew its thumb but lost a press or a drag, and its hidden range's arrow keys moved a value hydration then reset. The window was the island's fetch: React and its client renderer, about 66 kB gzipped and shared by every island, the Switch 2.5 kB, the Slider 9 kB. A native checkbox and range lose none of it.
- The renderer (DS-3's revisit trigger): `@astrojs/react` ships its client renderer only to a page with an island; in the pilot, the guide's 10 pages with a Switch or Slider carried it and the other 24 none. With DS-8 no input page carries it, and the pack-and-install test fails an inputs page with an island or a script.
- Consequences: an island sits in an `<astro-island>` element (`display: contents`), so a parent's child combinator (`.row > .avatar`) no longer reaches a hydrated component drawn in an Astro page; a descendant selector does. A page script that sets a property on a hydrated component's element is overwritten by React: it renders the component in a React island and passes the state as props.
- Why: one rule a family can copy without a choice of its own, a full look before any script, and no script on a page that draws no component that needs one.
- Rejected: `client:visible` (a component scrolled into view starts loading only then, so the lost-press window opens again below the fold); `client:idle` (above); `client:only` (no server markup: a shift when it draws, and nothing to read before); an Astro wrapper per component that hydrates itself (a second source beside the `.tsx`, the twin DS-3 rejects, and an island cannot draw it).
- Revisit if: the app's browser suites show a tap before hydration lost on a phone (DS-4), or a page's load slows measurably from components it draws off screen; or a custom Astro directive that hydrates on the first press and replays it is worth an integration every consumer registers.
