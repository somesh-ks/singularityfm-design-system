## DS-8: a component draws the native element where the browser already does the job, and Base UI only where it adds behaviour the browser lacks

- Status: active; amends [DS-4](DS-4.md) (which put Base UI under every control with state) and narrows [DS-7](DS-7.md) to the components that need a script
- Date: 2026-11-09
- Decision: the owner's call, on the overlays migration and the Button family, then "whichever is performant" for Switch and Slider. Every component stays React (DS-3) with one API: imported by name, placed with `className`, the same prop names, state shown as `data-*` attributes. What lies under it follows one test: does a native element already do the job and work before any script? Then the component draws that element and takes no client directive. Otherwise it is built on its Base UI primitive and hydrates with `client:load` (DS-7).
  - Native: Button, IconButton and Fab (a `<button>`, or an `<a>` with `href`); Dialog and Sheet (`<dialog>`: focus held inside, Escape, the scrim as `::backdrop`, opened by the page's own script); Select (the native `<select>` with its styled picker, and the phone sheet); the filter chip (a checkbox); the segmented choice (radio inputs); Switch (a checkbox with `role="switch"`) and Slider (a range input), as main drew them; Code's Copy button (the native IconButton). Menu is native too (a popover that `popovertarget` opens with no script) unless the menus family measures a behaviour only Base UI Menu gives.
  - Base UI: Field and Search field (Base UI's Field control, a native input under it, with Field.Root's label and validity in a React island's form); Avatar (the photo's fallback to its shape when it fails to load); the segmented nav (Base UI Tabs: the browser has no tabs).
- Why: Base UI's Dialog renders its popup through a portal that draws nothing in server HTML, so the app's scripts that find or clone a sheet at load find nothing, and an opener's tap before hydration is lost; its Button adds `tabindex="0"` (Safari then tabs to every button, against the reader's setting) and nothing a page uses. Industry systems split the same way: shadcn/ui draws Button and Input as native elements and puts a primitive under Dialog, Select and Switch; the uniform part is the API, not the primitive.
- Rejected: Base UI under every control (DS-4 as written: the costs above, for an API the native components already share); Base UI Switch and Slider hydrated on load (the owner's first pick, reversed for performance: a page that draws one loads React's client renderer, about 70 kB, and the controls, about 12 kB, and a press before hydration is lost, where the native ones answer from the first frame and the app's scripts that set `checked` and `value` keep working).
- Revisit if: a native element's behaviour falls short in a browser the readers use (a customizable select missing where the phone sheet does not cover it), or Base UI renders a portal's popup on the server.
