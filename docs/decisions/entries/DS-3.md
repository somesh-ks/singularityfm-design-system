## DS-3: the library's one component framework is React with Base UI

- Status: active; amended by [DS-4](DS-4.md) (Base UI for every control with state, Button and Field included), [DS-5](DS-5.md) (a deprecated .astro path called with `class` is a shim) and [DS-7](DS-7.md) (a stateful component hydrates with client:visible, where the page draws it)
- Date: 2026-11-07
- Decision: the owner's call. Every component in the library is React (`react` and `react-dom` ^19.3) and, where it has behaviour, is built on a Base UI primitive (`@base-ui/react` ^1.9.0, the version the app draws its islands with) for that behaviour and its accessibility. The `.astro` components move to `.tsx` one family per pull request; Astro stays the framework of the apps and their pages, not of the library. A static component (Button, Icon, Badge) renders on the server with no client directive and ships no script; one with behaviour hydrates only where it is drawn, with `client:visible` or `client:idle`. The look stays pixel-identical: a migration keeps each class name and the markup, so the stylesheets are untouched. `designSystem.test.ts` fails a new `.astro` file under `packages/design-system/src` (the ones left are a list each family pull request trims) and a `.tsx` component with no exports entry of its own.
- Exports: a React component is imported by its name with no extension (`@singularityfm/design-system/Button`), from an explicit entry per component. The `./*` pattern would map `Button` to `src/Button.ts`, which a case-blind disk (Windows, macOS) serves as `button.ts`. A migrated component's old path (`Button.astro`) maps to the same `.tsx` and is deprecated; it is removed in a breaking release once the app imports by name.
- Consumers: `react` and `react-dom` are required peers; `@base-ui/react` is an optional peer until the first component that uses it. An Astro app adds `@astrojs/react` and passes `className`, not `class`: the renderer drops a `class` prop before the component sees it.
- Why: one framework for the controls the app draws in its pages and in its React islands, so an island no longer rebuilds a control from `buttonClass()` and a hand-written element, and behaviour (focus, keys, dismissal, popovers) comes from one maintained primitive instead of a script per component.
- Rejected: keeping Astro components beside React twins (two sources for one control drift); Base UI for a control a native element already serves (a Button needs no primitive, and its root adds attributes and state).
- Revisit if: `@astrojs/react` starts shipping its client renderer to pages with no hydrated island, or a consumer appears that cannot run React.
